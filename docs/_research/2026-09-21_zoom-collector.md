# Zoom collector: meetings + AI Companion summaries, signed in from the management UI

Date: 2026-09-21. Type: Feature Investigation. Stack: Python 3 (FastAPI, `requests`, SQLite connection store with encrypted secrets), Nuxt 3 web UI, APScheduler.
API facts marked **spec** come from Zoom's official OpenAPI file (`endpoints.json`, downloaded and parsed on this date). **docs** means fetched from developers.zoom.us. **forum** means a devforum thread. Anything else is labelled `UNVERIFIED`.

```yaml

  depends_on:
    - docs/_research/2026-09-13_auth-approach.md      # §2: S2S app, scopes, :master 403
    - docs/_research/2026-09-21_management-ui.md      # connection store, vault, oauth_flows, callback vs paste_back
  reverses:
    - docs/plans/management-ui/spec.md:22             # "Zoom and Slack OAuth" out of scope → Zoom OAuth now in scope
  status: final
  owner_request:
    - collector for Zoom AI (AI Companion) and Zoom Meetings
    - must authenticate, and integrate with the management UI
```

## Summary

A Zoom collector already exists: `pipeline/collectors/zoom.py`, which uses a Server-to-Server (S2S) token from `pipeline/health.py:353`. The UI already has a Zoom connection form (`api/routers/connections.py:67`). But the collector has only ever pulled AI Companion summaries, it has never run against a live account, and it has a real bug: it sends `from`/`to` as `YYYY-MM-DD`. The spec requires `yyyy-MM-dd'T'HH:mm:ss'Z'` (`pipeline/collectors/zoom.py:79-80`).

The recommendation has two parts.

1. **Add user-managed OAuth sign-in** (a Zoom "General app", authorization code, callback mode) as a second `auth_mode` on the existing singleton `zoom` connection. Keep S2S as the other mode.
2. **Widen the collector** from "summaries" to "meetings". Merge three sources: the user's summary list, the user's previous scheduled meetings, and (in S2S mode only) the meeting report, which alone covers instant meetings and meetings the user joined but did not host. Add participants, an optional transcript, and a `normalize.py` adapter so Zoom reaches the digest.

Zoom rotates refresh tokens and allows only one live token pair per user and app. The token refresh therefore has to be single-flight: the whole read → refresh → write sequence runs under a lock. No such lock exists for connection-store secrets today.

- **Files**: 2 new (`pipeline/oauth_zoom.py`, `tests/test_oauth_zoom.py`) and about 12 changed. The list comes from codebase-analyst's "Change surface", trimmed because the connection stays a singleton.
- **Breaking changes**: none for existing S2S users. `auth_mode` defaults to `s2s` whenever `ZOOM_ACCOUNT_ID` is set.

## Research Questions

### Q1: Which Zoom app type, and who can create it?
Both S2S and General apps need the account owner, an admin, or the "Zoom for developers" role to create them (**docs** create/). S2S mints account-wide tokens and needs `:admin` scopes, which the creator's role must be able to grant (auth-approach §2.1). A **user-managed** General app "has access to only the user's authorized data" (**docs**). It needs only user-level scopes, and it works unpublished for its creator and for other users on the same account through Local Test (**docs**, paraphrased by the fetch summarizer). → Offer both. Default new connections to the General app, which is least-privilege and doesn't need admin-scope role grants.

### Q2: What are the OAuth mechanics?
- Authorize `https://zoom.us/oauth/authorize`, token `https://zoom.us/oauth/token`, revoke `https://zoom.us/oauth/revoke` (**docs**).
- Access token lasts 1 h. **Refresh tokens expire after 90 days** and must be replaced by "the latest refresh token" on every refresh (**docs**, fetched twice verbatim). This settles a conflict with library-docs' recollection of "15 years".
- **One token pair per user per app**: a new pair invalidates the previous one instantly (**forum** 127541, Zoom developer). A double refresh strands whichever caller loses.
- PKCE supported (`S256`/`plain`; "Public clients must use `S256`"). **Loopback redirects (`127.0.0.1`, not `localhost`) are for PKCE or native clients only, "not standard confidential OAuth clients"** (**docs**). A 2026-06-24 forum answer agrees. → Paste-back mode, which relies on a loopback redirect (`pipeline/oauth_gmail.py:10-13`), does **not** carry over to a confidential Zoom app. v1 supports only `callback` (https `PUBLIC_BASE_URL`, already required by `pipeline/oauth_flows.py:325-347`).

### Q3: What AI Companion data can the API return?
| Data | Endpoint (spec) | User scope / admin scope | Notes |
|---|---|---|---|
| List summaries | `GET /users/{userId}/meeting_summaries` | `meeting:read:list_summaries` / `:admin` | "hosted by the specified user"; MEDIUM; `from`/`to` ISO-Z; `time_filter_field` ∈ {summary_start_time, summary_created_time} |
| Summary body | `GET /meetings/{meetingId}/meeting_summary` | `meeting:read:summary` / `:admin` | LIGHT; fields incl. `summary_content` (Markdown), `summary_doc_url`, `summary_title`; `summary_overview/details/next_steps/edited_summary` still in schema (deprecated per auth-approach §2.3) |
| Transcript | `GET /meetings/{meetingId}/transcript` → `download_url` | `cloud_recording:read:meeting_transcript` / `:admin` | MEDIUM; accepts ID or UUID (ID = latest instance); returns `can_download`, `download_restriction_reason`, `auto_delete_date` |
| "My Notes", meeting questions | none | none | no public API as of 2026-07 (**forum** 142964) |
| Summaries of meetings attended, not hosted | none | none | host-only (**forum** 100590, Zoom staff; 143615 still unresolved 2026-05) |

Summary prerequisites (**spec**): host on Pro+, the host's "Meeting Summary with AI Companion" setting enabled, no E2EE.

### Q4: How are "yesterday's meetings" enumerated, including ones with no summary?
- `GET /users/me/meetings?type=previous_meetings` (`meeting:read:list_meetings`): "only supports scheduled meetings… does not return information about instant meetings", and returns at most 6 months (**spec**).
- `GET /report/users/{userId}/meetings?type=past|pastJoined` (`report:read:user:admin`, **admin only**, 1-month window): `pastJoined` = meetings the user "hosted or joined" (**spec**). This is the only way to list instant meetings and attended meetings, and it's available only in S2S mode. A 2021 forum report says it rejects `me`, so resolve the real user id through `GET /users/me` first (`UNVERIFIED` for 2026).
- The summaries list catches instant meetings **that have** a summary.
→ **Union, keyed on `meeting_uuid`**: summaries ∪ previous_meetings (both modes) ∪ report pastJoined (S2S only).

### Q5: How does this fit the management UI?
The Zoom connection is a hard-coded singleton (`pipeline/connections.py:131`, `_derive` at 265-270). The OAuth layer is provider-agnostic except for the `PROVIDERS` tuple (`pipeline/oauth_flows.py:40`), `_KIND_FOR_PROVIDER` and the if/else dispatch (`api/routers/oauth.py:68`, `:166-187`), and the provider ternaries in `web/components/OAuthDialog.vue:174,268,322`. The Gmail sequencing module (`pipeline/oauth_gmail.py`) is the template to copy.

### Q6: What does it take to keep a rotating refresh token alive unattended?
The daily run refreshes well inside 90 days. Every refresh must write the new refresh token before anything else happens, all under a per-connection lock, the way `pipeline/tokencache.py:65-90` does for MSAL. `invalid_grant` becomes a hard "sign in again" error, like `GmailAuthError` (`pipeline/health.py:400`).

## Findings

### 1. Current collector state (codebase, spec)
- The summaries `from`/`to` are sent date-only (`pipeline/collectors/zoom.py:79-80`), but the spec says ISO-Z. It may be rejected or silently widened; either way it's **wrong per spec**. Fix it no matter which auth mode is used.
- `ZOOM_SCOPES` (`pipeline/health.py:39-45`) requires `past_meeting`, `list_past_participants` and `report:read:user` admin scopes that the collector never calls. Health can fail on scopes the collector doesn't need.
- No participants, meetings without summaries, or transcripts are collected, despite the "meetings" wording in the README (`README.md:12`).
- `normalize.py:190-211` handles only `gmail_*`. Zoom items are stored but never become `NormalizedItem`s. This gap existed before this work; the Zoom adapter closes it for Zoom.
- Dispatch matches `source == "zoom"` exactly (`pipeline/collectors/__init__.py:92`). That's fine while the connection stays a singleton.

### 2. Connection model (codebase)
- `KINDS["zoom"] = _Kind(label_field=None, config=("account_id","client_id"), secrets=("client_secret",), required_secrets=("client_secret",))` (`pipeline/connections.py:131`). Gmail (`:133-140`) is the template for an optional `refresh_token` secret set by sign-in.
- `_Kind` has no "required only if" rule (`:120-126`, `:247-262`). Make `account_id` optional, and let `check_zoom` report what's missing for the chosen `auth_mode` instead of teaching the validator conditionals.
- `set_secret` (`:424-430`) is atomic for the database write only. It does not cover the token exchange.
- `materialize` (`:689-693`) and the `.env` seeding regex (`:536`) know only the three S2S keys.

### 3. OAuth machinery (codebase)
- `FlowStore`, nonce binding, `build_callback_url` and the FlowError family are reusable as they are (`pipeline/oauth_flows.py:135-347`).
- `oauth_gmail._client_credentials` reads the client id and secret from the connection store, not from the environment (`pipeline/oauth_gmail.py:130-138`). Copy that.
- `api/routers/oauth.py:126-140` maps FlowError subclasses to error codes once for every provider. Zoom errors that subclass the same bases get this for free.

### 4. Refresh-token race (codebase + forum)
The Test button (`api/routers/connections.py:318-335`) and the scheduled run (`pipeline/runner.py:137-139`) can both refresh at once. Because Zoom rotates refresh tokens and allows one pair per user, the loser gets `invalid_grant`. Worse, a late write can put a dead token back in the store. The repo has solved this before: `tokencache.locked()` holds a per-alias lock across load → refresh → save (`pipeline/tokencache.py:79-90`, used at `pipeline/health.py:319-342`). The lock is a `threading.Lock`, so it covers the API process, which also runs the scheduler (`api/scheduler.py`), but not a separate `python -m pipeline.collect` CLI process. That's the same limit M365 already accepts.

### 5. UI (codebase)
- The Sign-in button is gated to `gmail || m365` (`web/pages/connections.vue:104-111`).
- `KIND_FIELDS.zoom` lists only the S2S fields (`web/components/ConnectionDialog.vue:145-149`).
- `OAuthDialog.vue` decides "signed in" from `secrets_set.includes('refresh_token')` for Google. Zoom should use the same branch.

### 6. Transcripts (spec, forum, vendor)
Transcripts come from `/meetings/{id}/transcript`. The host setting "Allow hosts to view and manage transcripts after the meeting" (KB0076632) and the account setting "Allow users to retain transcripts generated by meeting summary…" (**forum** 142885) are both involved. Zoom staff say transcript access "is dependent on cloud recording" (**forum** 142964), and Recall.ai says transcripts need cloud recording, are English-only, and can take up to 24 h (vendor, 2026-09-15). They are large and sensitive. → Make them opt-in, off by default, and capped in size.

## Dissent / Contradictory Evidence

- **Is S2S simpler for a single owner?** web-researcher argues S2S is lower-friction for a person who owns their own Pro account: no 90-day expiry, no rotation race, no redirect registration. That's true, and it's why S2S stays a supported mode rather than being removed. The General app wins when the user isn't the owner, or can't get admin scopes granted, and on least privilege: S2S `:admin` scopes can read every user on the account. The owner's account situation is not known (see Open Questions).
- **Refresh-token lifetime.** library-docs recalled "15 years, rotates on use". The docs page, fetched verbatim twice, says 90 days. **Resolved in favour of 90 days.**
- **`auto_start_meeting_summary`.** Forum 133254 (2025-06) says `summary_content` is populated only when a meeting is created via the API with `auto_start_meeting_summary: true`. The spec lists only host settings as prerequisites. Read the forum report as applying to **API-created** meetings only. The collector already records `summary_available=False` instead of dropping the meeting (`pipeline/collectors/zoom.py:130-141`), so either reading is handled.
- **Loopback redirects.** The docs say loopback is fine for PKCE or native clients. The forum (2026-06) says it "will only work if you are doing PKCE public oauth flow". Both agree that a confidential web-style app can't use paste-back. Whether a Zoom General app can be configured as a secret-less public PKCE client is `UNVERIFIED`.
- **Transcripts without cloud recording.** Zoom staff: "dependent on cloud recording". KB0076632 describes "Meeting Summary with AI" transcripts without mentioning recording. The evidence conflicts, so live testing decides.

## Recommendation

### Decision

Extend the existing singleton `zoom` connection with **`auth_mode: "oauth" | "s2s"`**. Add **user-managed General-app OAuth** (authorization code, confidential client, `callback` mode only, scopes below) with browser sign-in from the management UI. Keep S2S working exactly as it does now. Rebuild the collector as a **meetings collector**: one `Item("meeting", uuid, …)` per meeting in the window, built from the union of the summaries list, `previous_meetings`, and (S2S only) the `pastJoined` report. Enrich each item with the summary body, participants (hosted meetings), and an opt-in transcript. Refresh tokens are **single-flight under a per-connection lock, and the new refresh token is persisted before the access token is used**. `invalid_grant` becomes a hard "sign in again" health error. Add a Zoom `normalize` adapter.

User-mode scopes: `meeting:read:list_summaries`, `meeting:read:summary`, `meeting:read:list_meetings`, `meeting:read:past_meeting`, `meeting:read:list_past_participants`, plus `cloud_recording:read:meeting_transcript` only when transcripts are enabled. `user:read:user` is needed for `GET /users/me` (`UNVERIFIED` exact name; check the scope picker). S2S-mode scopes: trim `ZOOM_SCOPES` to what the collector calls, and add `report:read:user:admin` for `pastJoined`.

### Rationale

- The owner asked for UI-driven authentication, and an S2S form is only credential entry. A General app lets anyone with the developer role sign in from the UI and hold only their own data (**docs** create/).
- Summaries are host-only whichever auth is used (**forum** 100590/143615), so user OAuth loses nothing on AI content. Only instant meetings and attended-meeting enumeration need S2S (the report endpoint is admin-only, **spec**). That's why S2S stays as a mode rather than going away.
- Keeping the singleton avoids breaking about 20 e2e assertions and the dispatch rule for a second Zoom identity nobody has asked for.
- Callback-only follows the Zoom docs: confidential apps can't use loopback redirects. Every other piece of the flow already exists and has been hardened (`oauth_flows.py`: nonce, TTL, single-use).
- The single-flight lock follows a pattern the repo already has (`tokencache.py`). Without it, the one-token-pair rule turns a routine race into an outage.

### Comparison Matrix

| Criteria | Dual mode, OAuth default (rec.) | Keep S2S only (fix bugs) | OAuth only, drop S2S |
|---|---|---|---|
| Sign-in from UI | Yes | No (credential form) | Yes |
| Works for non-admin user with dev role | Yes | Needs admin-scope grants | Yes |
| Least privilege | Yes (user scopes) in OAuth mode | No (account-wide `:admin`) | Yes |
| Instant + attended meetings listed | S2S mode only | Yes | No |
| Unattended durability | 90-day expiry; daily refresh keeps it alive | Best (no refresh token) | Same as rec. |
| Breaks existing setup | No | No | Yes |
| Effort | Medium | Small | Medium |
| **Overall** | **Recommended** | Acceptable if owner is account owner and wants no sign-in | Not recommended |

## Implementation Sketch

### Step 0: Fix the existing collector (both modes)
`pipeline/collectors/zoom.py:79-80`: `since.strftime("%Y-%m-%dT%H:%M:%SZ")`. Trim `ZOOM_SCOPES` to the calls actually made.

### Step 1: Connection kind (`pipeline/connections.py:131`)
```python
"zoom": _Kind(
    label_field=None,                                   # still a singleton
    config=("client_id",),
    optional_config=("auth_mode", "account_id", "redirect_mode", "include_transcripts"),
    secrets=("client_secret", "refresh_token"),
    required_secrets=("client_secret",),
),
```
`auth_mode` defaults to `"s2s"` when `account_id` is present, else `"oauth"`. `redirect_mode` accepts only `"callback"`. Extend `ZoomCreate` (`api/routers/connections.py:67`) to match.

### Step 2: `pipeline/oauth_zoom.py` (mirrors `oauth_google.py` + `oauth_gmail.py`)
- `build_auth_url(client_id, redirect_uri, state)` → `https://zoom.us/oauth/authorize?response_type=code&…`
- `exchange_code` / `refresh`: POST `https://zoom.us/oauth/token` with Basic `client_id:client_secret`. Return `access_token`, `refresh_token`, `expires_in`, `scope`.
- `start` / `finish_callback` sequence around `FlowStore`. `finish` stores `refresh_token` through `connections.set_secret`. Errors subclass `oauth_flows.FlowError`. `paste_back` start raises `InvalidCallbackConfig`-style "Zoom requires callback mode".
- Wiring: `PROVIDERS += ("zoom",)` (`oauth_flows.py:40`); `_KIND_FOR_PROVIDER["zoom"]="zoom"` and a zoom branch in `_start`/`_finish_callback` (`api/routers/oauth.py:68,166-187`).

### Step 3: Single-flight token (`pipeline/health.py`)
```python
class ZoomAuthError(Exception): ...          # refresh token dead → sign in again

_zoom_lock = threading.Lock()
_zoom_access: tuple[str, float] | None = None  # (token, expires_at) in-process cache

def zoom_token() -> str:
    view = connections.get("zoom")
    if view.config.get("auth_mode", "s2s") == "s2s":
        return zoom_token_response()["access_token"]          # unchanged path
    with _zoom_lock:                                           # whole read→refresh→write
        if _zoom_access and _zoom_access[1] - time.time() > 300:
            return _zoom_access[0]
        data = oauth_zoom.refresh(client_id, client_secret, connections.get_secret("zoom", "refresh_token"))
        connections.set_secret("zoom", "refresh_token", data["refresh_token"])  # persist FIRST
        _zoom_access = (data["access_token"], time.time() + data["expires_in"])
        return data["access_token"]
```
`invalid_grant` → `ZoomAuthError`. `check_zoom()` goes through the same function, so the Test button never refreshes separately. It checks the per-mode scopes and reports "sign in again" on `ZoomAuthError`.

### Step 4: Meetings collector (`pipeline/collectors/zoom.py`)
1. `summaries = list_summaries(token, lookback_start, until)`: ISO-Z, `summary_created_time`, paginate.
2. `scheduled = GET /users/me/meetings?type=previous_meetings&from&to` (date params per spec), filter by end time in the window.
3. S2S only: `joined = GET /report/users/{uid}/meetings?type=pastJoined&from&to`.
4. Merge by `meeting_uuid`. For each: `meeting_summary` (404 → `summary_available=False`, as now); `past_meetings/{uuid}/participants` when the user is host; transcript when `include_transcripts` (text capped at 200 KB, `download_restriction_reason` kept).
5. Payload keys: `topic, start_time, end_time, host_email, hosted: bool, participants[], summary_content, summary_doc_url, summary_available, transcript_text?`.

## Risks

- **Refresh-token loss (high impact, medium likelihood).** A crash between Zoom's refresh response and `set_secret` loses the only valid token, and the user must sign in again. Mitigation: persist before anything else, keep the critical section tiny, and make the health error say plainly "sign in again".
- **Cross-process refresh.** The CLI `python -m pipeline.collect zoom` in a separate process escapes the thread lock. Mitigation: have the CLI refuse OAuth-mode Zoom while the API is running, or add an `fcntl` file lock around the refresh. Pick one in the plan.
- **90-day idle expiry.** Only if the scheduler is off for 90 days. A health check shows it.
- **Endpoints never run live.** The whole Zoom path is spec-driven. Mitigation: a manual smoke task (`python -m pipeline.collect zoom --raw`) goes in the plan's verify list before the collector is marked done.
- **Sensitive content.** Summaries and transcripts include what other attendees said. Transcripts are off by default, go through the existing `redact` pipeline, and are capped.
- **Personal details.** Keep the callback host name out of tracked files (repo rule).
