# Domain collector: portfolio console, DNS/RDAP intel, name ideas, registrar purchase

Date: 2026-09-21. Type: Feature Investigation. Stack: Python 3 (FastAPI, SQLModel/SQLite, `requests`), Nuxt 3 + Quasar web UI, APScheduler.
Registrar policy facts marked **verified** were fetched from the vendor page on this date; the rest carry their source and are `UNVERIFIED` where noted. Design proposals are marked `PROPOSAL`.

```yaml
scope:
  topic: domain-collector
  depends_on:
    - docs/_research/2026-09-21_management-ui.md   # connection store, vault, OAuth flows, CSRF model
  status: final
  owner_request:
    - pull all public information for a domain: DNS, registration, MX / mail posture, URL/subdomain intel
    - generate domain name ideas
    - buy domains through the owner's Namecheap and GoDaddy accounts
    - one console for every owned domain, collected from Namecheap, GoDaddy, WordPress.com
  interpretation:
    - "url search" read as (a) availability search for candidate names and (b) URL/subdomain intel for a domain (CT logs, Wayback, urlscan). Confirm with owner.
```

## Summary

Build a separate **domains subsystem** inside signalslate rather than another 24h collector: a domain portfolio is state, not an event stream, so it gets its own tables and its own daily refresh job. It feeds the morning digest through a thin `domains` collector that reports only *changes* in the window: expiring soon, NS/MX changed, lock removed, auto-renew off. Registrar access is less open than it looks. The **GoDaddy** Domains API is free with ≥1 domain, but availability checks need ≥50 domains or ≥US$20/month average spend (verified). **Namecheap** turns the API on only after 20 domains, a $50 balance, or $50 spent in 2 years, and every call must come from a whitelisted IPv4 address (verified). **WordPress.com** has no documented domain API. An undocumented `/rest/v1.1/all-domains` endpoint exists and answers with an OAuth `global`-scope token. RDAP plus DNS covers every domain whatever the registrar, so it is the backbone. Registrar APIs add what only they know: auto-renew, pricing, authoritative availability, and purchase. Purchasing ships last, off by default, behind a server-side quote, a price cap and typed confirmation.

## Research Questions

### Q1: Which registrar APIs can list domains and buy them, and what does each require?
**Answer**: Namecheap is an XML API at `api.namecheap.com/xml.response` that takes `ApiUser`/`ApiKey`/`UserName`/`ClientIp`. It has `domains.getList`, `getInfo`, `check`, `create` and `renew`, plus `dns.getHosts`, `users.getPricing` and `users.getBalances`. Limits are 50/min, 700/hour and 8000/day, and only IPv4 addresses can be whitelisted (verified, Namecheap FAQ). GoDaddy uses v1 REST with `Authorization: sso-key KEY:SECRET`. The endpoints are `GET /v1/domains`, `/v1/domains/{d}`, `GET|POST /v1/domains/available`, `/v1/domains/agreements`, `/v1/domains/purchase/schema/{tld}`, `POST /v1/domains/purchase` and `/v1/domains/{d}/records`. The quota is 20,000 calls/month, and a test environment runs at `api.ote-godaddy.com`. v3 (`registration-quotes`, `registrations`) moves to Bearer PAT auth (`UNVERIFIED`, certbot #10733). WordPress.com is read-only at best: nothing is documented and there is no purchase API.

### Q2: Is the owner eligible for these APIs?
**Answer**: Unknown. It depends on the owner's accounts. GoDaddy (verified): any account with ≥1 active domain gets the Domains API (list, detail, DNS, purchase). **Availability checks** need ≥50 domains, ≥$20/month average spend, or a paid Discount Domain Club / Appraisal plan. The widely cited "50 domains or no API at all" rule is the **May 2024** policy. The current help page is looser, so treat community threads from 2024 as stale. Namecheap (verified): 20 domains, a $50 balance, or $50 spent in the last 2 years. The sandbox is available to anyone. The app must show "API not enabled for this account" as a normal connection state, not a crash.

### Q3: How are WordPress.com domains collected?
**Answer**: Three tiers. (1) **Best effort**: OAuth2 authorization-code flow (`public-api.wordpress.com/oauth2/authorize` → `/oauth2/token`) with `scope=global`, the scope the docs describe as granting "comprehensive access to user data across all WordPress.com services", then `GET /rest/v1.1/all-domains`. Probed on this date, that path returns 403 `authorization_required` while a nonexistent path returns 404, so the endpoint exists. Its response shape is undocumented and can change. (2) **Supported fallback**: paste or CSV import of domain names, then enrich each one via RDAP. (3) A `/rest/v1.1/me/sites` listing yields each site's primary domain. WordPress.com domains sit behind several backend registrars (CentralNic Reseller, Wild West Domains, Tucows, `UNVERIFIED`), which is why no unified API exists.

### Q4: What gives the full public picture for any domain?
**Answer**: DNS via `dnspython` 2.9.0: A, AAAA, CNAME, MX, NS, TXT, SOA and CAA, and mail posture from SPF, `_dmarc`, common DKIM selectors, `_mta-sts` plus the policy file, and BIMI. Registration data via **RDAP**, which has been authoritative for gTLDs since 28 Jan 2025 (ICANN), using the IANA bootstrap `https://data.iana.org/rdap/dns.json`. RDAP gives registrar, created/expiry dates, nameservers and EPP status codes. Many ccTLDs still lack RDAP (.de, .cn and .jp reported, `UNVERIFIED`) and need a WHOIS:43 fallback or an "unsupported" status. Subdomains and URLs come from crt.sh CT JSON (5 req/min, frequent 502s, so best effort), the Wayback CDX API, and optionally urlscan.io or VirusTotal (4/min and 500/day free, with a ToS limit on commercial use).

### Q5: How do name ideas and availability search work without leaking ideas?
**Answer**: Generate locally. Start with combinatorial rules (seed words × prefixes/suffixes × TLD list, plus TLD hacks). An optional second stage asks the Claude API for ideas from a description. Filter locally first: DNS NXDOMAIN plus RDAP 404 is a cheap, private signal. It is not authoritative, because premium, reserved and redemption-period names give false positives. Send only the shortlist to a registrar for the authoritative check with price and premium flag: Namecheap `domains.check` (batch around 50, `UNVERIFIED`) or GoDaddy `POST /v1/domains/available` (up to 500, needs the availability tier). Front-running is documented (the 2008 Network Solutions case), which is why checks should never go through third-party "domain search" sites.

### Q6: How is purchasing made safe?
**Answer**: Neither API has a dry run or idempotency key. Namecheap `domains.create` charges the account balance immediately. GoDaddy `purchase` charges the payment method on file after `agreementKeys` and `agreedAt`/`agreedBy` are accepted. So all safety is app-side. Steps: a server-issued quote (price, premium flag, renewal price, 5-minute TTL). A per-purchase and daily spend cap in config. The user retypes the domain name to confirm. A `DomainPurchase` intent row with a UUID and a unique constraint to block double submits. No add-ons. Master switch `DOMAINS_PURCHASE_ENABLED=false` by default. The whole flow is tested first against Namecheap sandbox and GoDaddy OTE. The sandbox's availability universe differs from production, so a green sandbox run does not prove production works.

## Findings

### 1. Portfolio is state; it needs its own tables and job (codebase)

- Collectors are stateless `(since, until) -> CollectionResult` functions dispatched by source-id prefix (`pipeline/collectors/__init__.py:28`, `:37`, `:79`). `CollectedItem` (`pipeline/db.py:53`) is an event row deduped per `(source, external_id)`, with per-source watermarks. If the portfolio were re-emitted every run as fake events, that dedupe and backfill logic would break.
- New `SQLModel` tables belong in `pipeline/db.py`. Migrations are additive columns only via `_add_missing_columns()` (`pipeline/db.py:119`), which skips NOT NULL columns without a Python default (`pipeline/db.py:83`). New tables are created by `create_all`, so no migration tool is needed.
- The scheduler manages one hard-coded job, `JOB_ID = "daily_digest_run"` (`api/scheduler.py:46`). A daily domain refresh needs a second job id and a small refactor of `reschedule()`.
- `PROPOSAL`: the refresh job writes `DomainSnapshot` rows. A `domains` collector (source id `domains`) returns `Item`s for snapshot *diffs* inside the window. The digest gets "3 domains expire in <30d; example.com NS changed" without the portfolio pretending to be mail.

### 2. Connections, vault, OAuth reuse (codebase)

- `KINDS: dict[str, _Kind]` (`pipeline/connections.py:129`) declares config, secrets and required fields per kind. Add three kinds: `namecheap` (config `api_user`, `username`, `sandbox`; secret `api_key`), `godaddy` (config `environment` = prod|ote; secrets `api_key`, `api_secret`; later `pat`), and `wordpress` (config `client_id`; secrets `client_secret`, `access_token`). Each needs a `materialize()` branch (`pipeline/connections.py:650`) and a `known_sources()` extension (`pipeline/health.py:516`).
- Fernet vault (`pipeline/crypto.py`) needs no change. `secret_values()` (`pipeline/connections.py:511`) already feeds `redact()` for every stored secret, so new keys are scrubbed from logs automatically.
- `oauth_flows.py` is provider-agnostic apart from `PROVIDERS = ("google", "microsoft")` (`pipeline/oauth_flows.py:40`). Add `"wordpress"` and a `pipeline/oauth_wordpress.py` modelled on `oauth_google.py`. Paste-back and HTTPS callback modes both apply. The docs describe no refresh token (docs fetched this date), so a lapsed token means signing in again, surfaced as a connection health state.
- **Registrant contact data** (name, address, phone, email) is needed for every purchase and is PII. Store it as an encrypted secret on the registrar connection, not in `data/config.json`.

### 3. Namecheap specifics (verified FAQ plus docs via agent)

- Eligibility: 20 domains, a $50 balance, or $50 spent within 2 years. Whitelist **IPv4 only**. Limits are 50/min, 700/hour and 8000/day per key. The sandbox (`sandbox.namecheap.com`) is a separate account; test domains exist in the registry's test environment, and coupons don't work there.
- `ClientIp` must be the app's public egress IPv4. On a home host with a dynamic address, calls start failing silently when the ISP rotates the IP. `PROPOSAL`: the health check fetches the current egress IP (for example `https://api.ipify.org`) and reports "whitelist 203.0.113.7 in Namecheap". Never auto-edit the whitelist; there is no API for it anyway.
- Responses are XML. Parse with `defusedxml.ElementTree` (stdlib `xml.etree` is XXE-prone; no XML dependency exists today). Wrapper libraries (`PyNamecheap` forks) are stale, so a hand-rolled `requests` client of about 200 lines is safer.
- `domains.create` requires all four contact roles (Registrant/Tech/Admin/AuxBilling) and charges the account balance with no confirm step. `users.getBalances` should gate the buy button.

### 4. GoDaddy specifics (verified help page plus endpoint list via agent)

- Tiers: ≥1 domain → Domains API. ≥50 domains or ≥$20/month average → plus availability. Paid plans add the Valuation API. 20,000 calls/month on the free tier. Rate limit 60 req/min per endpoint, with `429` and `RateLimit-Reset` headers (`UNVERIFIED`).
- `GET /v1/domains` lists owned domains with `expires`, `renewAuto`, `locked`, `privacy` and `status`. v3 does not yet cover listing owned domains, so use v1 for inventory.
- Purchase: fetch `/v1/domains/agreements?tlds=…&privacy=false` → build a body that matches `/v1/domains/purchase/schema/{tld}` → `POST /v1/domains/purchase` with `consent.agreementKeys`, `agreedAt`, `agreedBy`. No payment-method selector was found (`UNVERIFIED`).
- Handle `403 ACCESS_DENIED` / `ACCOUNT_NOT_ELIGIBLE` as the connection state "API tier insufficient". Keep inventory working when availability is blocked.

### 5. RDAP + DNS as the registrar-neutral backbone (dns-intel)

- RDAP client: `whoisit` 4.x (v4.0.5, 2026-09) uses `requests` + `dateutil`, matching the codebase's `requests` convention. It is maintained (December 2025) and bootstraps from IANA. `asyncwhois` adds WHOIS:43 fallback for non-RDAP ccTLDs, but is async. `PROPOSAL`: `whoisit` first, WHOIS fallback deferred until a real owned ccTLD needs it.
- DNS: `dnspython` sync resolver in a bounded `ThreadPoolExecutor` (the codebase is sync `requests` plus thread pools). Point it at the LAN resolver, not bulk traffic to 1.1.1.1 or 8.8.8.8. DoH JSON (`dns.google/resolve`) as a second opinion.
- Snapshot fields to diff: NS set, MX set, A/AAAA, SOA serial, CAA, SPF/DMARC strings, registrar, expiry, RDAP status set. `clientTransferProhibited` removed is a hijack or transfer warning. `redemptionPeriod`/`pendingDelete` on a *watched* (not owned) domain signals it may free up.
- Mail posture checks per domain: SPF present and ≤10 lookups, DMARC `p=` value, DKIM on common selectors (`google`, `selector1`, `selector2`, `k1`, `default`), MTA-STS TXT plus `https://mta-sts.<d>/.well-known/mta-sts.txt`, BIMI. Parked domains should publish `v=spf1 -all` and `p=reject`. That makes a good digest finding: "parked domain accepts spoofed mail".

### 6. Name generation + availability (dns-intel, contrarian)

- Stage 1, combinatorial: seeds × affixes × TLDs, length and hyphen filters, TLD-hack splits. No dependency, deterministic, testable.
- Stage 2, optional LLM: Claude API (`claude-haiku-4-5-20251001` for cheap bulk ideas) takes a short brief and returns JSON candidates. This is the project's first LLM dependency; it can be skipped until synthesis (phase 3) brings one in anyway.
- Pipeline: generate → local DNS+RDAP prefilter (private) → registrar check on the top N (authoritative, priced) → save as `DomainCandidate` with price and premium flag. Premium flag or price above the cap blocks purchase.

### 7. Build vs reuse (contrarian)

- Domain Locker (MIT; Angular + Deno/TypeScript; Postgres or Supabase) does portfolio monitoring, SSL, DNS and expiry alerts, but has no purchasing or name generation. DomainMOD (PHP/MySQL) imports from GoDaddy, Namecheap and 10 more, but also has no purchasing.
- Both are different stacks with their own databases and UIs. Neither fits the digest pipeline, the connection vault, or the purchase requirement. Reuse *ideas* (field sets, alert types) but not code. Running Domain Locker alongside is a valid alternative if the owner only wanted monitoring.

### 8. API + UI placement (codebase)

- `api/routers/domains.py`, included at `/api` like the others (`api/main.py`). CSRF is header plus Origin (`api/security.py:36`, `:156`) and applies automatically. **Nothing extra guards a spending POST today**, so the purchase route adds its own quote-token check and cap.
- `web/pages/domains.vue` plus a tab in `web/app.vue:7-11`. Types and fetchers go in `web/composables/useApi.ts`. Dialogs follow `web/components/ConnectionDialog.vue`. Views: inventory table (source registrar, expiry, auto-renew, lock, NS provider, mail posture badge), domain detail (DNS, RDAP, CT subdomains, history diff), Ideas (generate → check → buy).

## Dissent / Contradictory Evidence

- **GoDaddy threshold.** The contrarian agent and 2024 community threads (Let's Encrypt forum, Domain Name Wire, Cloudron) say accounts under 50 domains get *no* API. The current GoDaddy help page, fetched on this date, says ≥1 domain unlocks the Domains API and the 50-domain / $20 tiers gate only *availability*. Resolution: trust the vendor page, but design for either outcome, because the 2024 change shipped without notice and could shift again. Confidence is medium until the owner's key is tested.
- **GoDaddy auth churn.** certbot #10733 reports a move to PAT bearer tokens (`UNVERIFIED`). v1 sso-key still documented for v1/v2. Keep the auth header behind one function.
- **WordPress.com.** Two agents concluded "no API". The live probe shows `all-domains` exists behind auth. Both are true: it is *undocumented*, not absent. Treat it as a best-effort adapter, with CSV/RDAP as the fallback.
- **Sandbox trust.** Namecheap says the sandbox works like production against registry test environments. Community reports cite divergence (.co.uk flow, premium pricing display; `UNVERIFIED`). Sandbox passing is necessary, not sufficient.
- **Availability heuristics.** RDAP 404 / NXDOMAIN are private but give false "available" for premium, reserved and redemption names. Authoritative checks leak intent to the registrar. The two-stage design accepts that trade-off: the registrar sees only the shortlist.

## Recommendation

### Decision

Build an in-app **domains subsystem** in four phases, with RDAP+DNS as the registrar-neutral backbone and registrar adapters as enrichment. Ship read-only first; purchasing comes last and is disabled by default.

- **Phase A: inventory + intel (read-only).** Tables `Domain` (name as lower-case punycode, `source`, `registrar_account`, `owned|watched`), `DomainSnapshot` (JSON of DNS/RDAP/mail posture plus hash). Adapters: Namecheap `getList`, GoDaddy `GET /v1/domains`, WordPress.com `all-domains` (best effort) plus manual/CSV add. Lookup service: dnspython + whoisit + mail posture. Console page. On-demand "inspect any domain" (CT subdomains, Wayback) with no persistence required.
- **Phase B: monitoring → digest.** Daily refresh job; `domains` collector emits diff items (expiry ≤30/7 days with auto-renew off, NS/MX/A change, lock removed, mail posture regression, watched domain entering redemption).
- **Phase C: ideas + availability.** Combinatorial generator → local prefilter → registrar check → candidate list. Claude-API ideation as an opt-in.
- **Phase D: purchase.** Quote → confirm → buy, Namecheap first (balance-funded, easy to cap by keeping a small balance), GoDaddy second. Sandbox/OTE mode per connection.

### Rationale

- The portfolio is state, and `CollectedItem` is an event log (`pipeline/db.py:53`). Separate tables plus a diff collector keep both models honest and still put domain news in the morning page.
- RDAP+DNS works for every domain regardless of registrar or API tier. Registrar APIs are gated (Namecheap 20/$50; GoDaddy availability 50/$20) and WordPress.com is undocumented, so the console must not depend on them to be useful.
- Namecheap's balance-funded purchasing puts a hard ceiling on worst-case spend. That, plus server-side quotes and caps, answers the codebase gap that nothing guards spending routes today.
- Existing OSS (Domain Locker, DomainMOD) covers monitoring only, in other stacks. It can't reach the digest, the vault, or purchasing.
- Every piece reuses existing seams: `_Kind` spec, vault, `redact`, `oauth_flows`, router/CSRF, page pattern. Only one dependency is non-trivial (`dnspython`).

## Implementation Sketch

### Step 1: Registrar adapter protocol (`pipeline/domains/registrars/__init__.py`)

```python
@dataclass(frozen=True)
class RegistrarDomain:
    name: str                 # lower-case, punycode
    expires_at: datetime | None
    auto_renew: bool | None
    locked: bool | None
    privacy: bool | None
    nameservers: tuple[str, ...]

@dataclass(frozen=True)
class Quote:
    name: str
    available: bool
    premium: bool
    price: Decimal            # first-year, account currency
    renewal_price: Decimal | None
    currency: str

class Registrar(Protocol):
    kind: str                                   # "namecheap" | "godaddy" | "wordpress"
    def list_domains(self) -> list[RegistrarDomain]: ...
    def check(self, names: Sequence[str]) -> list[Quote]: ...          # NotSupported for wordpress
    def purchase(self, quote: Quote, years: int, contact: Contact) -> PurchaseResult: ...
```

Expected failures (not eligible, IP not whitelisted, 429) return typed statuses, matching collectors' "never raise for expected failures" rule.

### Step 2: Namecheap client (XML, defusedxml)

```python
from defusedxml import ElementTree as ET
NS = {"nc": "http://api.namecheap.com/xml.response"}

def _call(cfg, command: str, **params) -> ET.Element:
    base = "https://api.sandbox.namecheap.com" if cfg.sandbox else "https://api.namecheap.com"
    r = requests.get(f"{base}/xml.response", timeout=30, params={
        "ApiUser": cfg.api_user, "ApiKey": cfg.api_key, "UserName": cfg.username,
        "ClientIp": cfg.client_ip, "Command": command, **params})
    root = ET.fromstring(r.content)
    if root.get("Status") != "OK":
        raise NamecheapError([e.text for e in root.iterfind(".//nc:Errors/nc:Error", NS)])
    return root
```

`list_domains` pages `namecheap.domains.getList` (`PageSize=100`). Respect 50/min.

### Step 3: Lookup service (`pipeline/domains/lookup.py`)

`inspect(name) -> Snapshot` runs DNS record types, mail posture and RDAP concurrently in a `ThreadPoolExecutor(max_workers=8)`. Each part records `ok|error|unsupported` rather than failing the whole snapshot. `snapshot_hash` over normalized fields drives diffing.

### Step 4: Purchase flow (`api/routers/domains.py`)

1. `POST /api/domains/quotes {name, registrar_id}` → the server calls `check`, stores a `DomainQuote` row (uuid, price, premium, expires in 5 min) and returns it.
2. `POST /api/domains/purchases {quote_id, confirm_name, years}` → rejected unless all of these hold: `DOMAINS_PURCHASE_ENABLED`, quote unexpired, `confirm_name == quote.name`, `not premium or allow_premium`, `price <= DOMAINS_MAX_PRICE`, today's total + price ≤ `DOMAINS_DAILY_CAP`, and no existing `DomainPurchase` row for the quote (unique on `quote_id`). The row is inserted as `pending` **before** the registrar call and updated to `succeeded|failed` after. On a timeout or unknown outcome it stays `unknown` and is reconciled against `list_domains` on the next refresh. Never retry automatically.
3. The UI dialog shows first-year and renewal price, premium badge and registrar, and requires typing the domain.

### Step 5: Digest collector

Add a `domains` branch to `dispatch()` (`pipeline/collectors/__init__.py:79`) returning `Item(item_type="domain_alert", external_id=f"{name}:{kind}:{snapshot_id}", …)` for diffs whose `DomainSnapshot.taken_at` falls in `[since, until)`.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Owner's accounts below Namecheap/GoDaddy API thresholds | Medium | High | RDAP+CSV inventory works without them; show eligibility state; Namecheap $50 balance unlocks it |
| Accidental or double purchase | Low | High | Disabled by default, quote token, typed confirm, caps, unique intent row, no auto-retry, small Namecheap balance |
| Premium / add-on price surprise | Medium | Medium | Block premium by default; GoDaddy `privacy=false` explicit; show renewal price |
| Namecheap IP whitelist breaks on WAN IP change | High (home host) | Medium | Health check reports the current egress IP vs failure; document static egress |
| WordPress.com `all-domains` changes or needs cookie auth | Medium | Low | Adapter marked best effort; CSV/RDAP fallback |
| GoDaddy policy or auth changes again (PAT) | Medium | Medium | Single auth function; typed 403 handling |
| crt.sh / RDAP flakiness, ccTLD gaps | High | Low | Per-part status, backoff, cache; "unsupported TLD" state |
| Registrant PII leakage | Low | Medium | Store contacts encrypted in vault; covered by `redact()` |
| Idea front-running | Low | Medium | Local prefilter; registrar check only on shortlist; no third-party search sites |
